# 写作框架信号路由表

本表帮你判断要不要用框架、用哪个、取哪部分。**框架是可选脚手架，不是必选模具。**

## 重要原则

- **Framework 可选**：可以选一个完整框架；可以只取一个框架的局部（比如只用 SCQA 的 S+C 铺开场，不用 Q+A）；可以组合多个框架的局部；也可以不用任何框架（当编辑判断本身已经够支撑结构时）。
- 这 10 个框架**完全独立、无优先级、无默认**--没有"首选 SCQA"这种事
- 如果两个框架都像，选择 `best-for` 描述更贴近用户**原始诉求和题材现状**的那个
- 不强制逐步确认。选定后向用户告知选择和理由即可。写到一半发现框架不适合，可以丢掉，不要为了走完框架而硬撑。
- 框架文件里的"骨架步骤"是参考，不是必须逐步执行的 checklist。按需取用。

## 10 个框架速查表

| Framework | 一句话定位 |
|---|---|
| `scqa` | 商业分析、深度长文、产品分析--题材有公认背景 + 一个反常变化（"以前是 X，现在变成 Y"）时使用 |
| `pyramid` | 技术方案、报告、决策文档--需要从结论到支撑、逐层展开的说服性写作 |
| `bluf` | 短文、说服性观点、给忙人看的稿子--读者需要在读到第一句就知道该做什么决定时使用 |
| `inverted-pyramid` | 新闻类、资讯类公众号、SEO 文章--题材是"已发生的事件"且读者只看前两句就要拿到核心信息 |
| `paul-graham-essay` | 探索型 essay、自己也不确定答案的思考文--用写作发现答案，不是为预设结论辩护 |
| `islands-bridges` | 当你对题材只有模糊的直觉（Foggy Intuition），说不清答案、材料散乱、不知道文章结构时--用这个框架边写边发现 |
| `fast-writing` | 有 deadline 的高效写作--当你不能像学校那样花一学期写一篇文章，需要让写作流程融入日常生活、能在工作日间隙稳定产出时使用 |
| `tim-urban-explainer` | 当你要把一个复杂概念（AI / 科学 / 技术 / 历史 / 心理）讲给完全不懂的读者，而且需要他们读完真正"懂了"而不是"听过了"--用这套方法把抽象变具体、把困难变好玩 |
| `sivers-compression` | 要写一篇极短、句句压缩的观点文--当你脑子里已经有一团乱思路、想把它砸成一份 50-300 字的骨架，并直接把骨架本身当作文章发布时使用 |
| `stratechery-analysis` | 分析一个具体的科技公司决策、产品战略转向、平台动作、行业拐点观察，并从中提炼出一个可复用的战略框架 |

## 题材特征 -> 候选框架

下面列出常见的题材/场景特征。**这不是优先级表，是匹配引擎**：
- 一行可能有多个候选--读完候选框架的 `best-for` 和"信号"节再决定
- 同一题材完全可能用不同框架--选择跟用户**当下意图**最贴的
- 也可能不用任何框架--特征不明确或编辑判断已足够时，直接起草

### 按"用户已经知道想说什么"分

| 题材特征 | 候选 |
|---|---|
| 用户**已有清晰论点**，想为它铺好让读者关心的开场 | `scqa` |
| 用户**已有结论**，需要从结论到证据自上而下展开 | `pyramid` / `bluf` |
| 用户**说不清答案**，想边写边发现 | `paul-graham-essay` / `islands-bridges` |
| 用户**有一团乱思路**，想压成最短骨架 | `sivers-compression` |
| 用户对题材**只有模糊直觉**、材料散乱 | `islands-bridges` |

### 按"题材类型"分

| 题材特征 | 候选 |
|---|---|
| 产品分析、行业评测、产品/平台战略分析 | `scqa` / `stratechery-analysis` |
| 复杂概念解释（AI / 科学 / 技术 / 历史） | `tim-urban-explainer` |
| 新闻、资讯、事件播报 | `inverted-pyramid` |
| 技术方案、决策文档、报告 | `pyramid` |
| 给老板/忙人看的备忘录、提案 | `bluf` |
| 探索型 essay、思考随笔 | `paul-graham-essay` |
| 创业复盘、产品方法论分享 | `stratechery-analysis` / `scqa` |

### 按"写作约束"分

| 约束 | 候选 |
|---|---|
| 有 deadline、需要快速产出 | `fast-writing` / `bluf` / `sivers-compression` |
| 想写极短文（300 字以内） | `sivers-compression` |
| 想写深度长文 | `tim-urban-explainer` / `paul-graham-essay` / `scqa` |
| 读者只看前两句就要拿到核心 | `inverted-pyramid` / `bluf` |
| 读者愿意跟着你一起思考一整篇 | `paul-graham-essay` / `islands-bridges` |

## 选定后

1. 加载 `references/frameworks/<chosen>.md`，按需取用（不必逐步执行）
2. 向用户告知选择和理由
3. 写到一半发现框架不适合，丢掉它，不要硬撑
4. **也可以不选框架**--编辑判断 + 素材本身能支撑结构时，直接起草

## 写完一篇之后

记录：
- 选用了哪个 framework，还是没用 / 只用了局部
- 为什么
- 写作过程中有没有丢掉框架？为什么？

这些记录可以反过来优化本路由表--如果某个题材类型反复触发丢弃，说明该框架的匹配规则需要调整。
