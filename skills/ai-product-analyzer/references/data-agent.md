# Data Agent 专项评估（BI / Text-to-SQL）

Data Agent 护城河不在模型能力，在**上下文深度**。模型是公共基础设施，上下文是私有资产。Text-to-SQL 是伪命题——模型能力已足够，瓶颈在"用户问题 → 正确表+正确定义+正确过滤"的中间环节。

## 维度 1：上下文深度（核心维度）

六层标尺——产品能理解多深的业务语义：

| 层级 | 内容 | 能力 | 难度 |
|------|------|------|------|
| L1 Schema | 表名、列名、数据类型 | 基础 Text-to-SQL | 低 |
| L2 Usage | 查询历史、表血缘、join 模式 | 推断常见用法 | 低 |
| L3 Annotation | 人工标注的业务含义 | 理解业务意图 | 中 |
| L4 Code | 管道代码级理解（表怎么产生） | 区分相似实则不同的表 | 高 |
| L5 Institutional | 组织文档（Slack/Docs/Notion） | 理解业务事件和内部术语 | 高 |
| L6 Memory | 从更正和对话中学习 | 持续提升准确率 | 最高 |

**Meaning Lives in Code**：schema 描述表的形状和用法，真正含义在产生数据的代码中。管道逻辑捕获了 schema 不会显现的假设和业务意图。

检验方法：问一个需业务判断的问题。"上季度收入增长？"→ L1 可能选错表，L5 知道 12 月日志故障导致缺失，L6 记得上次纠正过排除测试账号。

评分：仅 L1-L2 = 无竞争力；L1-L4 = 有壁垒缺组织理解；L1-L5 = 懂业务的分析师；L1-L6 = 飞轮

## 维度 2：推理闭环

关键不是一次答对，是**迭代收敛到正确**。五项检验：

| 能力 | 描述 | 权重 |
|------|------|------|
| 错误检测 | 发现中间结果异常（零行、数量级错误） | 高 |
| 自主重试 | 调查错误原因、调整策略、重新执行 | 高 |
| 跨轮上下文 | 多轮保持完整语境 | 中 |
| 主动澄清 | 指令模糊时主动提问 | 中 |
| 合理默认 | 无回复时用合理默认值推进 | 低 |

**Guide the Goal, Not the Path**：高度规范性 prompt 反而降低质量。给高层目标，让模型选路径。

反面模式：One-shot 答完即走；固定脚本式执行；出错只报错不修正。

## 维度 3：信任基础设施

四层信任：

| 层级 | 内容 | 检验 |
|------|------|------|
| 透明性 | 展示推理过程和假设 | 用户能看到每步怎么来的？ |
| 可验证性 | 链接底层查询和原始数据 | 用户能自己验证？ |
| 权限控制 | 严格数据访问权限 | 直通式还是另起一套？ |
| 评估体系 | 持续准确率监控 | 有系统化回归测试？ |

评分：黑盒输出 = 低；展示 SQL 不解释 = 中；完整推理链+可验证 = 高；+持续评估+权限直通 = 最高

## 维度 4：集成深度

三级：独立工具 → 多入口（Slack+IDE+Web） → 工作流引擎（可复用、自动化）

**Less is More**：暴露全部工具集导致混乱。Agent 不是人——冗余对人可容忍，对 Agent 致命。

## 维度 5：上下文维护成本

| 检验 | 静态（旧） | 动态（新） |
|------|-----------|-----------|
| 构建 | 手工 | LLM 自动提取 + 人工精炼 |
| 更新 | 季度/年度 | 每日/实时 |
| 来源 | 仅 schema | Schema+代码+文档+对话 |
| 暴露 | BI 工具内嵌 | API/MCP 开放 |
| 维护 | 高 | 低 |

**飞轮检验**：用得越多越好吗？不会 → 上下文是死的。

## 市场定位

三类玩家：数据引力平台（基础设施+用户基数，风险是 AI 非原生）、AI 数据分析公司（AI-native，缺基础设施护城河）、Context Layer 专家（专注上下文，需与平台集成）

## 评估输出：25 分制

逐项 1-5 分：

| 维度 | 分数 |
|------|------|
| 1. 上下文深度（达 L__） | /5 |
| 2. 推理闭环 | /5 |
| 3. 信任基础设施 | /5 |
| 4. 集成深度 | /5 |
| 5. 维护成本 | /5 |
| 总分 | /25 |

20-25 = 深度关注；15-19 = 有亮点有短板；10-14 = 观望；<10 = 反面教材。+ 市场定位判断。
