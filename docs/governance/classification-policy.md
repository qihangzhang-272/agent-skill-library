# 分类治理规则

这份文档解决一个问题：技能库不是越分越细越好，也不是所有外部内容都应该复制进来。分类的目标是让 agent 能更快判断该用什么能力、从哪里取、如何组合，而不是把资料摆得整齐。

## 两层分类

| 层级 | 适合放什么 | 维护方式 |
| --- | --- | --- |
| 大类 | 投资、产品、写作、前端设计、技术、开发范式、运营等长期能力域 | 只在 `sections/` 和 `docs/sections/` 做索引、来源、调用链和优先级 |
| 小技能 | 边界清楚、可独立触发、可被 agent 读取的技能包 | 满足收录条件后放进 `skills/`，并登记到 `catalog/skills.yml` |

大类不应该为了完整而复制大量正文。大类的价值是帮 agent 路由：这个任务属于哪个能力域，应该看哪些技能、索引或工作流。

小技能可以复制，但必须能独立说明触发场景、输入、输出、来源和验证方式。

## 默认策略

外部内容先进入索引，后进入技能包。

| 内容类型 | 默认处理 |
| --- | --- |
| 完整 skill 包 | 如果许可证、来源和运行边界清楚，可以迁入 `skills/` |
| 单个 `SKILL.md` 或少量配套文件 | 可以作为小技能迁入，但要补齐来源和触发场景 |
| 大型 repo | 只做来源索引，除非明确抽取某个自包含子目录 |
| 网页 prompt 集合 | 只记录入口、用途和选择策略，不复制 prompt 正文 |
| UI 库源码、CLI、运行时工具 | 只记录文档入口和适用场景，不复制源码 |
| 一次性实验结果 | 放本地实验区，不进入正式技能库 |

## 迁入 `skills/` 的最低条件

新增技能进入 `skills/` 前，必须满足：

1. 有明确的 agent 工作问题。
2. 有稳定触发场景。
3. 有清楚输入和预期输出。
4. 来源、上游 URL、commit 或捕获时间可追溯。
5. 许可证或复制边界清楚。
6. 迁移范围和排除范围写清楚。
7. 不依赖隐藏服务、私人路径或不可复现环境。
8. 能用一次静态检查或实际调用验证。

不满足这些条件时，只能作为候选或来源索引。

## 分类调整规则

- 优先合并功能重叠的小类，不新增语义接近的 section。
- 如果一个技能同时适合多个大类，以主要调用链为准，其他关系写到 `pipeline_role` 或文档中。
- 如果某个大类只有一两个技能，先保留在现有大类索引下，不急着拆新 section。
- 如果某个外部项目很大，只抽取可复用的小技能；项目本身留在来源索引。
- 如果迁入后发现技能无法独立复用，应降级为索引，或用 wrapper 说明限制。

## 与现有目录的关系

- `sections/` 是大类入口。
- `docs/sections/` 是大类的来源、调用链和索引。
- `catalog/skills.yml` 是技能总账。
- `skills/` 只放已经确认可复用的小技能包或保守迁移子集。
- `plugins/` 是分发结果，不作为分类源头。

因此，分类调整优先改 `sections/`、`docs/sections/` 和 `catalog/skills.yml`；只有确认可以迁入时，才改 `skills/`。
